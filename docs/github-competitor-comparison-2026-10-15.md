# 组卷助手：新一轮 GitHub 竞品功能对比

调研日期：2026-10-15（北京时间）。

本轮重新筛选较高人气、具备真实产品功能的 GitHub 项目，替代 2026-10-10 报告作为后续选型依据。旧报告保留为历史记录。

配套交付：[后续发展规划](product-roadmap-2026-10-15.md) · [逐项对标验收表](competitor-acceptance-2026-10-15.csv) · [版本与人气快照](research/github-competitor-snapshot-2026-10-15.json) · [源码证据索引](research/github-competitor-code-evidence-2026-10-15.json)。

## 1. 决策结论

**建议把“组卷助手”发展为“面向考研自学者的本地学习工作台”：资料可追溯，错误能纠正，题目能迁移，整卷能完成，复习能持续。**

新一轮真正值得对标的是 DeepTutor、OpenMAIC、PageLM 这类完整 AI 学习产品，以及 AnythingLLM、Oppia、Moodle、LearnHouse、Algorithm Visualizer、Kolibri、Habitica 的成熟能力。它们的人气明显高于上一轮几十星的直接竞品，但必须按学习任务比较，不能用 Stars 替代质量。

这次最关键的变化：

1. **“加一个 AI 聊天、知识库、每日任务”已经没有辨识度。** 当前 DeepTutor 连题库、错题、计划复习、学习路径、来源引用和多媒体阅读都已有官方说明，源码还包含掌握度工具。我们的目标应是把可靠考研题、具体错因、步骤评分、实验验证和延迟复测串成同一条训练链。[S01][C01]
2. **“能生成课件和动画”也只是追平。** OpenMAIC 已提供课堂生成、交互实验、讨论、白板及课程导出。我们需要题目参数驱动的可验证实验，及直接解决当前错题的短课，而非再次收集泛教学动画。[S02]
3. **已有能力不重新立项。** 主观题、四档复习、八类图解、45 个 OS 实验、桌宠、番茄钟及答案册已有代码和实现文档。新工作是打通、扩展和产品化。[L01]–[L08]
4. **真正可以保留并放大的优势是“可复核”。** 本地判题已有评分点总和、学生原文证据、低置信度待复核及人工确认；OpenMAIC 当前短答接口的特定异常分支会回退给一半分数。这个局部差异有源码证据，但不能外推为整体 AI 正确率更高。[C02][L03]
5. **主线优先级：资料证据中心 → 错因补弱 → 模考训练 → 四科实验联动。** 桌宠任务成长、随身复习和资料生成学习包随主线逐步上线。

本轮交付是研究和规划，不是这些新功能已经实现。没有完成竞品安装与相同任务的并排实测，不能现在宣布“全面超越”。“完全超越”的放行标准见第 7 节。

## 2. 方法与选型

### 2.1 人气门槛与筛选

- 主池要求采集时 **至少 1,000 Stars**、具备可识别的产品或交互能力。纳入 10 个上一轮未重点分析的新仓库。
- 从 GitHub 仓库搜索的 AI tutor、学习平台、flashcards、mock interview 等方向筛选，再按任务相关性人工核验；不是宣称穷尽 GitHub 或建立全站排行。
- 优先近期维护的项目；Algorithm Visualizer 保留为高人气、成熟但更新较慢的能力标杆，明确降权其维护信号。
- 不将纯题解目录、课程资源合集、提示词或算法依赖算成完整竞品。Anki、FSRS、Super Productivity 已在旧轮研究及本地实现中吸收，本次作为回归基线，不占新候选名额。
- 面试方向搜索到 liftoff（1,528 Stars，最后 push 2023-12-23）和 offerPilot（747 Stars）；前者维护较旧、后者未达本轮门槛，且当前可运行产品主线是考研，暂列观察。面试资料文件存在不等于已有面试产品。两项仅为搜索观察，未做深度功能核查。

## 5. 逐个竞品：吸收什么，怎样形成优势

### S01 · DeepTutor：首要正面对标

**观察（D/C）**：当前固定版本不是早期“上传 PDF 解题”演示。README 列出统一能力运行时、资料阅读、Book、Practice、Task Board、伙伴、记忆及插件；学习空间明确说明错题与计划复习。抽查 `mastery/tools.py` 可见状态、测验、评分、修复问题、评估和路径修订工具；文件说明计算交给学习引擎。

**对我们意味着什么**：聊天、RAG、计划复习、伙伴人格和学习路线都只能算基础对齐。不能把“有 FSRS”直接当作胜出证明，因为本次未核实对手调度算法。

**超越设计（P）**：每次训练关联原题版本、正式评分点、具体误区和实验状态；把“看懂讲解”与“独立解出新题”分开；计划只推荐用户时间内可完成的训练，并保留可解释选择依据。

**验收**：相同的页号/偏移混淆案例，从首次错答到七天后未见变式，完整记录帮助次数、来源和得分；按既定 rubric 比较与 DeepTutor 的完整流程。不能只截聊天回答做对比。

### S02 · OpenMAIC：交互课堂与可编辑教学产物

**观察（D）**：资料生成大纲与场景、课件/测验/交互实验/PBL、教师和多角色讨论、白板、语音、PPTX/HTML/课程 ZIP。离线导出会内嵌可取得的资源，但获取失败资源会保留 URL 并报告，不能称所有导出天然无外链。工作台支持恢复会话和场景修订。

**源码观察（C02）**：当前 `quiz-grade/route.ts` 收题干、作答、满分、可选评分提示，返回分数与短评；JSON 提取或解析异常时设为约半分。这里只描述该接口分支，不断言全平台都如此。

**超越设计（P）**：错一道题可开启 3–8 分钟微课，参数来自原题，关键结论由确定性模型验证；最后必须完成未见变式。沿用本地评分证据校验，异常转待复核。课程导出带题目、实验输入、来源、字幕和资源完整性清单。

**验收**：课堂生成、继续编辑、打断提问、测验、导出/导入均有任务用例；再增加“错误定位 → 实验验证 → 重新独立作答”完整用例。只做一个播放器不能宣称追平课堂产品。

### S03 · PageLM：学习资料的多种产出

**观察（D）**：资料问答、Cornell 笔记、卡片、带提示测验、播客、语音转写、作业规划、ExamLab、辩论和学习伙伴；支持本地模型配置。卡片的具体调度算法、ExamLab 的严格考试语义和评分质量本轮未确认。

**超越设计（P）**：从一章资料生成可编辑学习包，产物统一绑定段落/页码，生成题先进入既有审核队列；卡片接入现有 FSRS；播客只围绕已确认错因和有效材料，听完可立即口述回忆。

**验收**：笔记、卡片、题目、音频不是四份互不关联的输出；改正源资料后提示哪些产物过期，旧学习记录仍可回看。资料生成失败保留原资料和已完成部分。

### S04 · AnythingLLM：本地资料与模型产品化

**观察（D）**：工作区、资料导入与引用、本地/云模型、模型路由、记忆、定时任务和 Agent 工作流。README 明确多用户权限与嵌入式聊天的部分能力仅 Docker 版，不能当作桌面默认功能。

**超越设计（P）**：对齐本地模型与引用体验，进一步按题号、学科、年份、资料版本过滤检索；默认先检索已核验题解，再检索用户资料。模型缺依据时让用户补材料，不自动拼接不相关解析。

**验收**：100 个已标注资料问题检查引用命中和定位；同题不同年份/版本不会串答；关闭 AI 后搜索、刷题和复习仍完整可用。

### S05 · Oppia：把错因变成可教的分支

**观察（D/C）**：互动探索模拟一对一辅导；`skill_domain.py` 明确有 misconception、feedback、prerequisite_skill_ids、rubric 以及修订操作。

**超越设计（P）**：在当前解析区展示一条“接下来补什么”，后台维护技能关系，不恢复用户删去的大知识地图。先纠正误区，再练条件变化后的题，而非重复原题答案。

**验收**：至少 12 个跨三科人工编排的错因分支，每个有先修检查、提示层级、迁移题和复测；允许用户修改诊断，避免一次错误永久贴标签。

### S06 · Moodle：考试必须是一个完整状态流程

**观察（D/C，局部）**：Moodle 是完整学习平台；源码考试类声明进行中、超时、完成、放弃，包含成绩和复核相关方法。代码内容接口限流后，通过固定提交 raw 文件抽查；完整保存结果见代码证据索引。未穷尽题型、插件与学校管理。

**超越设计（P）**：整卷快照锁定后建立独立答卷；选择题和主观题共用答题卡；严格模考到时交卷，训练模式允许超时，二者明确分开；卷后直接从错因进入实验和 FSRS。

**验收**：刷新、主窗关闭、崩溃恢复、重复交卷、到点交卷均不产生两份成绩；已生成答案册不提前通过答题 API 泄露；更改模板不改变旧答卷。

### S07 · LearnHouse：内容可组织，练习可评测

**观察（D/C）**：课程、内容编辑、集合、作业、讨论、播客、互动组件、编程自动评分和白板。README 把支付、SSO、多组织列为 Enterprise。作业服务源码包含作答/重试状态，以及参考解和隐藏测试用例的展示控制；30+ 语言是 README 声明，本轮未逐一运行。

**超越设计（P）**：把“课程”缩成服务一组错因的短课包；编程训练除通过测试外，还检查执行过程、边界条件和复杂度说明。可选扩展真实编译器，但不能把当前 JSCPP 直接改名为完整 C++ 运行环境。

**验收**：课程编辑、练习提交、重试、评分、隐藏用例保护分别覆盖；考研用户不必先建立班级和课程管理后台才能做题。

### S08 · Algorithm Visualizer：代码与状态连接

**观察（D）**：从代码生成运行可视化；算法内容和多语言 tracer 分布在其它仓库，主仓库并非完整能力清单。该仓库 push 停留在 2024-06-09，适合取方法，不应描述为近期活跃。

**超越设计（P）**：补齐数据结构、组成原理、网络，与已有 OS 实验共同形成四科实验。支持“先预测下一步 → 执行 → 看反例 → 回答考试问题”；能从错题载入同一组参数。

**验收**：算法输出、代码事件和可视化状态相互一致。要声明超越其整个算法目录前，必须另外冻结 algorithms/tracers 子仓库和全部语言范围；当前研究不以 OS 的 45 个实验充当全平台覆盖。

### S09 · Kolibri：离线产品不只是离线网页

**观察（D/C）**：官方定位为无互联网也能教与学的平台；考试模型保留内容题源、随机种子、顺序约定与数据模型版本。完整设备同步冲突语义未实测。

**超越设计（P）**：学习包同时携带题目、资料片段、实验规格、资源校验和可选进度；断网可以执行训练；联网后按事件合并，来源更新不能覆盖个人笔记和改判。

**验收**：断网导入并完成学习包，另一设备接续，重复导入不重复加题/奖励/复习事件；缺资源明确阻止依赖它的任务。

### S10 · Habitica：让陪伴依赖真实学习

**观察（D）**：完成行为影响等级、生命与金币；代码和美术许可分开。README 明示 2026-08-04 起暂停接收公开代码 PR，不能只看最近 push 就判定贡献开放。

**超越设计（P）**：复用现有桌宠角色，用独立回忆、纠正错误、实验挑战完成驱动成长；不同科目得到不同纪念物；支持休息日和低负担模式，弱化断签损失。只加积分不是有效学习。

**验收**：同一学习事件只奖励一次；挂机计时、反复看答案、重复导入不刷奖励；一键从桌宠进入下一任务，退出成长模式不影响核心功能。

## 6. 融合原有优势的三个目标场景

以下为产品设计，尚未实现。它们决定新功能怎样合并，而不是再加十个孤立页面。

### 场景 A：一道错题，真正纠正

408 地址转换做错 → 选择具体错因 → 资料中定位页号/偏移定义 → 分层提示 → 原题参数进入现有实验 → 改一个条件预测结果 → 无提示完成变式 → 人工确认掌握 → FSRS 安排回访 → 桌宠结算有效任务。

组合来源：Oppia 的误区教学 + DeepTutor 的学习上下文 + 我们的题库、实验、FSRS 与桌宠。优势要靠迁移正确率和流程完成率验证。

### 场景 B：一章资料，变成一周训练

导入资料 → 保留页码和原图 → 学习包草稿（笔记/题目/卡片/音频）→ 用户审核 → 按剩余时间安排今日任务 → 电脑练题、手机回忆 → 修改源资料时显示受影响产物。

组合来源：AnythingLLM 的引用体验 + PageLM 的多产物 + Kolibri 的离线分发 + 既有导入审核与 FSRS。

### 场景 C：一套模考，变成下一轮补弱

选择有版本的年度蓝图 → 生成题卷与固定快照 → 独立混合答卷 → 严格考试计时/恢复/交卷 → 主观题步骤复核 → 区分不会、粗心、读题和时间分配 → 生成可编辑三日补弱任务 → 一周后换题复测。

组合来源：Moodle 的考试状态 + OpenMAIC 的互动讲解 + 本地同快照答案册、可复核评分和桌面计时。

## 7. “完全超越”的明确标准

用户要求按完全超越规划，因此**不再沿用旧报告“核心模块达到 90% 就算完成”的标准**。但必须让比较对象和范围透明。

1. **范围先冻结**：第 4–5 节的目标学习任务并集，细化为配套 CSV 的逐项条目；每个条目必须指明竞品证据、本地状态、目标、验收和依赖。未知能力在验证前保持未知，不能当 0 分。
2. **对齐项 100% 通过**：每个被纳入的功能有完整流程，不是按钮或演示；核心失败一项即不放行，不用桌宠、题库数量等额外优势抵扣。
3. **新增优势另验**：三个完整场景要能独立完成，且比较相同题目、资料、设备和模型条件；不能用接口数量替代体验。
4. **质量、可靠性和成本分别比较**：引用准确性、判题误差、原有回归、恢复能力、耗时和模型成本均保留原始结果。性能比较不得只挑成功案例。
5. **学习效果需要纵向证据**：7 天、30 天延迟复测与未见变式表现单独测量；初期样本只做探索，不宣称保证提分。
6. **全产品范围不能偷换**：学校管理、多租户商业功能、通用 Agent 全生态、全算法/语言目录与多人游戏均在范围登记中明示不纳入本轮。若未来要求“每个项目所有功能逐项全覆盖”，这些都须另立研究和工程预算；本规划不会把该任务宣称已完成。

允许的结论应为“在已公开的考研学习任务范围内，达到全部对齐要求，并在指定闭环任务中优于固定版本”。目前状态是**已完成静态调研，尚未完成并排验收**。
